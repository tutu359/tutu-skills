# 视频随手记整理

将观看视频时记录的碎片化内容重构为逻辑完整、细节充分、方便检索和复习的 Markdown 知识笔记。忠实保留用户记录的信息，同时补足理解所需的逻辑，并明确处理补充、校正和不确定内容。

## 默认行为

- 收到原始笔记后直接整理并交付最终 Markdown，不输出思考过程、工作汇报或多余开场白。
- 将 `$tidy-note <笔记来源>` 直接解释为“读取该来源，整理内容并生成 Markdown 笔记”，不要求用户补充“请整理”等提示语。
- 默认采用“完整整理”强度：不只改写原句，还解释理解原笔记所必需的概念、原因、机制和关系，但不主动扩展成超出原笔记范围的教程。
- 只有用户明确要求“深度研究”“全面展开”或“补充更多相关知识”时，才扩大知识边界并增加延伸内容。
- 若用户要求“忠实整理”或“不要补充”，只重构原有信息并做必要的语言润色。
- 若用户指定标题、模板、详细程度、输出路径或保留原顺序，优先遵从用户要求。
- 不因轻微歧义中断工作。只有不同理解会实质改变整篇笔记时才提问，否则采用最合理解释并标明不确定性。

## 零提示调用与输入解析

支持用户只给出 Skill 名称和一个或多个笔记来源：

```text
$tidy-note G1随手记.txt
$tidy-note ./notes/线程池.md
$tidy-note /绝对路径/课程速记.docx
$tidy-note [用户附加的笔记文件]
$tidy-note https://example.com/my-video-notes.txt
```

按以下顺序处理：

1. 将 Skill 名称之后的所有文件名、路径、附件或 URL 识别为待整理的笔记来源，不把它们当作普通聊天文本。
2. 对相对路径先按当前工作目录解析；再检查当前任务的附件和可访问文件。不要凭文件名猜测内容。
3. 读取来源中的正文。支持纯文本、Markdown，以及当前环境能够可靠提取文本的文档或 PDF；需要专用文档能力时使用对应工具。
4. 对 HTTP 或 HTTPS 文件链接直接获取其文本内容。若链接需要登录、权限或已失效，简洁说明无法读取，并请用户重新授权或上传文件。
5. 若一次提供多个来源，默认分别生成笔记；仅当它们显然属于同一主题或用户要求合并时才合并。
6. 若用户只调用 `$tidy-note` 而没有提供任何来源，才请求用户提供文件或粘贴原始笔记。
7. 除非读取失败或存在会实质改变结果的歧义，不发送确认问题，直接完成整理。

文件名或链接本身只用于定位笔记内容。不要仅根据名称生成笔记，也不要将链接目标页面的无关导航、评论或广告混入正文。

## 内容边界

- 将用户的随手记视为核心素材，不虚构视频讲者说过的话、案例、数字、观点、时间戳或引用。
- 修正明显的错别字、术语拼写、语病和标点，不改变原意；首次出现专业缩写时补充全称或中文解释。
- 使用与原笔记相同的主要语言。中英混合笔记默认整理为中文，并保留必要的英文术语。
- 优先采用行业通行译法，避免生硬直译；没有可靠中文译法时保留英文并用中文解释。
- 保留用户给出的代码、命令、参数、公式、时间戳、个人感悟和重点金句，不因重构而遗漏。
- 将补充知识写成自然、准确的说明，但不得伪装成视频原话。与原记录发生冲突的内容必须在“补充与校正”中说明。

## 第一阶段：理解和提取

先在内部分析原始记录，不向用户展示冗长的中间过程。

### 1. 确定主题与范围

1. 推断视频的核心主题、所属领域和知识边界。
2. 判断输入是一条连续知识主线，还是多个互不相关的主题。
3. 多个主题互不相关时，分别成篇；若必须输出为一篇，则使用清晰的顶级模块隔开。
4. 不把一个局部概念扩写成超出原笔记范围的完整教科书。
5. 默认将正文收束为 2～4 个核心模块；原始信息较密集时可增加，但避免把几行速记扩成十余个大章节。

### 2. 拆分原子信息

识别并分类每条有效内容：

- 核心概念、定义和术语
- 特点、结论和重点金句
- 原因、机制和因果关系
- 步骤、流程和操作方法
- 参数、数字、版本和边界条件
- 示例、场景、优缺点和注意事项
- 代码、命令、配置和日志
- 对比、映射和概念之间的关系
- 用户的个人感悟、吐槽和疑问
- 疑似错字、事实错误及待确认内容

不要遗漏独特信息。合并重复表达时保留其中新增的限定条件和细节。

### 3. 处理特殊碎片

- 将类似“大对象？”的问号式记录视为待展开主题。能够可靠回答时补成独立小节；不能可靠回答时收入“待确认问题”。
- 将只有名词的记录与上下文建立关系，不要简单生成词典式定义。
- 将半句话恢复为书面表达；如果存在两种同样合理的解释，保留更贴合上下文的一种并标注推测。
- 仅当用户明确表达主观判断，或明确标注“我的想法/感悟/吐槽”时，使用“个人感悟”标签。不要把讲者观点或 AI 补充冒充用户感悟。
- 保留用户提供的时间戳并放到对应标题或段落附近；不得自行生成时间戳。

## 第二阶段：逻辑重构

按知识的内在理解顺序组织内容，不机械照抄输入顺序。根据主题选择最合适的结构。

### 概念原理型

```text
背景与问题 → 概念定义 → 核心特点 → 工作原理 → 关键机制 → 局限与应用
```

### 方法教程型

```text
目标与前提 → 准备条件 → 操作步骤 → 示例 → 常见问题 → 最佳实践
```

### 问题解决型

```text
问题表现 → 原因分析 → 解决方案 → 工作机制 → 代价与风险 → 适用场景
```

### 观点课程型

```text
主题背景 → 核心观点 → 分论点与论据 → 案例 → 启示 → 行动建议
```

章节数量服从内容，不强行限制为固定数量。相邻知识点存在明显的前置、因果、对比或包含关系时，使用过渡句说明关系。

## 第三阶段：深度扩写

围绕每个核心知识点，按需要回答以下问题：

1. 它是什么？
2. 为什么会出现或为什么需要它？
3. 它如何工作或如何执行？
4. 它与前后概念有什么关系？
5. 它解决了什么问题，又带来什么代价？
6. 它适用于哪些场景，有哪些限制或常见误解？
7. 是否需要示例、代码、流程或对比才能真正理解？

控制扩写质量：

- 优先补充解释链条，而不是堆砌更多术语。
- 只扩展与原始知识点直接相关的内容。不要自行增加完整工作流、检查清单、最佳实践或大量应用建议，除非原笔记已经涉及或用户明确要求。
- 每个原子知识点通常扩写为一至两个短段落或一个短列表；复杂概念可适当增加，不按固定字数灌水。
- 使用具体且短小的例子帮助理解；每个难点通常最多补充一个示例，且外部补充示例不得暗示来自原视频。
- 对用户只记录了名称但没有展开的核心概念，补充到能够独立复习的程度。
- 对原笔记已经解释清楚的内容进行精炼，不换词重复多遍。
- 不添加与主题仅有松散联系的百科知识。
- 不为单个补充点创建大章节；优先并入最相关的知识模块。
- 原始信息很少时，宁可保留“待确认”，也不要用猜测填满版面。

## 第四阶段：校正和核验

- 区分“文字规范化”和“事实更正”：明显拼写错误可直接修正；会改变知识含义的更正必须说明。
- 对版本敏感、可能变化、专业性强、包含精确参数或记忆不确定的信息进行核验。
- 优先使用官方文档、标准、论文和其他一手来源；技术问题优先采用对应版本的官方资料。
- 在相关段落附近放置简洁来源链接，不把笔记变成资料目录。
- 若无法核验，使用“待确认”“可能是”或“根据上下文推测”等明确措辞，不把推测写成事实。
- 外部资料与原笔记冲突时，保留原笔记想表达的概念，并在“补充与校正”中解释准确说法和版本差异。

## 第五阶段：生成元信息

在正文开头生成方便检索的元信息：

- **标题**：概括具体主题，避免“视频笔记”“学习记录”等空泛标题。
- **Tags**：生成 3～5 个标签，覆盖内容类型、所属领域和核心对象，例如 `#视频笔记 #Java #JVM #G1GC`。不生成与正文无关或过度宽泛的标签。
- **Summary**：用一句完整的话说明“这篇笔记讨论什么，以及最重要的结论是什么”。
- **来源**：仅当用户提供视频名称、作者或链接时填写。
- **时间**：仅当用户提供录制、观看或整理日期时填写，不使用当前日期冒充视频信息。

## 排版规范

- 只使用一个一级标题，从二级标题开始组织正文；标题层级连续，不从 `##` 跳到 `####`。
- 使用短段落解释知识，使用列表表达并列项，使用表格表达具有重复字段的对比或映射。
- 适度加粗关键词和字段名称，不连续加粗整段文字。
- 使用引用块承载用户原话、重点金句、警告或明确的个人感悟，并标明其性质。
- 使用带语言标识的代码块呈现代码；短命令、参数、类名和配置项使用行内代码。
- 仅在三步以上流程或多方关系用文字难以说明时使用 Mermaid；简单内容使用文字或列表。
- 除模板中的个人感悟标记外，避免装饰性 emoji、过多分隔线和花哨排版。
- 保持术语、大小写、数字单位和中英文空格风格一致。
- 确保 Markdown 可直接渲染，不输出未闭合的代码块、表格、链接或 Mermaid 块。

## 核心总结规则

- 使用 3～5 条编号结论总结全文精华。
- 每条结论都应能独立表达完整认识，而不是只写一个关键词。
- 优先总结概念本质、关键机制和实践影响，不机械复制章节标题。
- 不在总结中引入正文未出现的新事实。

## 输出与保存

- 用户直接粘贴笔记并要求整理时，默认返回完整 Markdown 正文，不附加额外解释。
- 用户以 `$tidy-note <笔记来源>` 形式零提示调用时，默认生成一个 `.md` 文件，并在完成后只返回简短结果和可点击文件链接。
- 用户要求“生成 Markdown”“保存为笔记”或明确需要 `.md` 文件时，将结果保存为 `.md` 文件，并同时给出可点击文件链接。
- 单文件输入默认使用 `<原文件名>-tidy.md`；若主题标题更清晰，也可使用主题生成简洁文件名。无法判断主题时使用 `tidy-note.md`。
- 多文件分别处理时为每个来源生成独立文件，并保持来源与输出文件名可对应。
- 遵守当前环境对用户交付目录的约定；没有约定时保存到当前工作目录。
- 不覆盖已有文件；若同名文件存在，增加简短主题、日期或数字后缀。

## 最终质量检查

交付前逐项确认：

1. 原笔记中的每个独特知识点、代码、金句、疑问和个人备注都已覆盖。
2. 标题具体，Tags 与正文相关，Summary 准确概括内容。
3. 章节顺序符合知识理解逻辑，不是原始碎片的简单重排。
4. 每个核心概念都获得足够解释，逻辑断点已经补全。
5. 错字、术语和书面表达已经规范化，没有误改原意。
6. 用户感悟、讲者观点和外部补充没有相互冒充。
7. 精确参数、版本信息和争议事实已经核验或明确标注待确认。
8. 补充内容服务于理解，没有无依据扩写或离题百科内容。
9. 核心总结包含 3～5 条完整结论，且没有引入新信息。
10. 标题、列表、表格、代码块、分隔线和链接均为有效 Markdown。
11. 全文详细但不重复，专业但易读，可脱离原始碎片独立复习。

## 示例处理策略

当输入包含：

```text
Garbage-First 垃圾优先
Regin化，可预测停顿，增量回收
大对象？
Card table 和 Remembered set
```

执行以下处理：

- 将 `Regin` 规范为 `Region`。
- 生成类似 `# G1 垃圾收集器：Region 化、回收策略与跨区引用` 的具体标题，以及 `#视频笔记 #Java #JVM #G1GC` 等相关标签。
- 重建“背景与特点 → Region 布局 → Garbage-First 含义 → 大对象 → 跨代/跨 Region 引用”的结构。
- 将“大对象？”展开为 Humongous Object 小节；涉及具体阈值或版本参数时先核验再写入。
- 解释 Card Table 与 Remembered Set 的职责、差异和协作流程，不只改写原句。
- 将过度简化或具有版本差异的说法放入“补充与校正”，不得悄悄覆盖。
- 用 3～5 条完整结论总结 G1 的内存布局、回收策略和引用跟踪机制。
